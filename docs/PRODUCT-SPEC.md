# 产品规格：个人知识库助手

> 状态：v1 · 2026-10-28 ｜ 赛道：AI Agent 智能助手（自拟选题）
> 一句话：**别的助手帮你找资料，它帮你发现资料之间的关系，并逼你输出。**

---

## 1. 定位

**产品名（暂定）**：织识 / Loom — 把碎片织成结构。

**解决的痛点**：收藏即遗忘。学生与知识工作者每天存入大量 PDF、网页、笔记，但——

- 存进去就再没打开过（收藏夹坟场）
- 想找时只记得"好像在哪看过"
- 新旧资料**观点冲突**时没人提醒，导致记错
- 攒了一堆素材，真要写东西时还是从零开始

**为什么现有工具不行**：笔记软件是"仓库"（要你自己整理），AI 问答是"搜索框"（问一次答一次）。中间缺的是**一个会主动整理、会指出矛盾、会逼你产出的角色**——这正好是 Agent 该干的事。

---

## 2. 用户与一天的故事

**Persona**：大三学生小林，同时准备课程论文、实习面试、竞赛。

| 时间 | 发生什么 | 产品介入 |
|---|---|---|
| 早 8:00 | 打开页面 | **今日简报**：昨天存了 4 条，其中 2 条与你论文笔记相关；1 条与旧笔记矛盾 |
| 午 12:30 | 看到一篇公众号文章 | 粘贴链接 → 自动炼制：摘要、标签、关联到已有 3 条笔记 |
| 晚 20:00 | 要写文献综述 | 选中 6 条素材 → **生成提纲**（每条都带出处） |
| 周日 | 复盘 | **周报**：本周新增 17 条、3 处冲突待裁决、5 条该复习 |

---

## 3. 差异化：三个"别人没有"

| # | 能力 | 为什么值钱 | 技术实现 |
|---|---|---|---|
| 1 | **冲突检测** | 新人资料与旧笔记观点矛盾时主动提示，而不是等你记错 | 新内容入库 → 检索 top-k 相似旧笔记 → LLM 判定「支持 / 矛盾 / 重复」→ 产出冲突卡 |
| 2 | **主动简报** | 打开就有，不是问了才有；这是"助手"与"搜索框"的分水岭 | 定时/进入页面触发 → 聚合新增、待复习、冲突、关联 |
| 3 | **以输出为目标** | 不做"回答问题"，做"帮你写完" | RAG 检索 → 提纲生成 → 每条论点挂引用 → 导出 Markdown |

> 这三条同时命中评分表：Agent 自主决策（8%）、创新性（25%）、实用性（10%）。

**反面清单**（做了就掉档）：纯聊天问答、只做关键词搜索、知识图谱炫技但无实际用途、做成 Notion 克隆。

## 4. 功能清单

### MVP（必须，第 1 周）

- [ ] 三种入库：拖文件（PDF/MD/TXT）、粘贴 URL、粘贴纯文本
- [ ] 自动炼制：摘要（3 句）、标签（3–5 个）、自动关联已有笔记
- [ ] 混合检索 + **回答必带引用**（点开看原文片段）
- [ ] 知识库列表：搜索、按标签筛选、按时间排序

### 冲奖（第 2 周）

- [ ] **冲突卡**：矛盾/重复提示 + 「采纳新的 / 保留旧的 / 并存」三选一（HITL）
- [ ] **今日/本周简报**：新增、冲突、待复习
- [ ] **提纲生成**：选 N 条 → 生成带引用的写作提纲
- [ ] 间隔复习：按遗忘曲线排「该复习」

### 明确不做

- 多人协作 / 分享
- 移动端 App
- 富文本编辑器（用 Markdown 够了）
- 知识图谱 3D 可视化（好看但零分，2 天成本）

## 5. 数据模型（在现有骨架上的增量）

```ts
interface Source {                 // 一条被收藏的原始材料
  id: string;
  kind: "pdf" | "url" | "text" | "image";
  title: string;
  url?: string;
  createdAt: number;
  summary: string;                 // 3 句摘要（炼制产物）
  tags: string[];
  chunks: Chunk[];                 // 切块 + 向量
}

interface Chunk {
  id: string;
  sourceId: string;
  text: string;
  index: number;
  embedding?: number[];
}

interface Relation {               // ★ 差异化核心
  id: string;
  fromId: string;                  // 新内容
  toId: string;                    // 旧笔记
  kind: "supports" | "contradicts" | "duplicates";
  confidence: number;              // < 0.7 不提示
  rationale: string;               // 为什么矛盾（给用户看的解释）
  status: "pending" | "accepted" | "dismissed";
}

interface ReviewItem { noteId: string; dueAt: number; intervalDays: number }
```

**设计要点**：`Relation.rationale` 是必须的——只告诉用户"这两条矛盾"而不说为什么，等于没做。

## 9. 技术方案

```
入库：文件/URL → 解析(pdf-parse / cheerio) → 清洗 → 切块(800字/重叠120)
     → embedding(bge-m3) → 存储(pgvector 或 sqlite-vec)

检索：query → 向量召回 top20 + BM25 召回 top20 → RRF 融合 → rerank top5
     → 拼 prompt（带出处编号）→ 流式生成

冲突检测：新 chunk → 召回 top5 相似旧 chunk → NLI 式判定
         → {"kind","confidence","rationale"} → confidence ≥ 0.7 才建 Relation

简报：每日聚合（新增 / 冲突 / 待复习）→ 模板渲染（非 LLM，省成本）
```

**隐私叙事**（创新分支点）：默认本地优先（IndexedDB + 浏览器端 embedding），只有生成阶段走云端。这句写进文档，就能自然引到端侧推理。

**成本**：单条入库约 1.5k tokens；100 条 ≈ 15 万 tokens，DeepSeek 约 ¥0.2。

## 11. 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 冲突检测准确率低，误报多 | 核心卖点变笑话 | 阈值 0.7 + 只说"可能矛盾" + 展示原文对照让用户自己判断 |
| 扫描版 PDF 解析失败 | 演示翻车 | 只承诺文本型 PDF；扫描件走 OCR 兜底并明确提示 |
| 演示像搜索引擎 | 掉到 70 分档 | 视频必须从"冲突卡"开始，不从提问开始 |
| 首版没有真实数据 | 效果不可感 | 提前准备 12 条真实素材（论文/公众号/课程笔记），预置在 demo 账号 |
| embedding 成本/延迟 | 入库慢 | 批量 + 异步，先返回"已入库，正在炼制" |
